## 摘要
边缘LLM部署不仅受模型大小和精度影响：推理后端、硬件平台、内存流量和功耗管理都会影响延迟和效率。我们提出了Hydra，一个面向边缘SoC上LLM推理的通用模式、阶段感知的工作负载特征化框架。Hydra使用共享的逐提示计时模式对HuggingFace Transformers和llama.cpp进行插桩，并将这些记录与硬件遥测数据融合，从而在预填充和解码阶段实现性能、系统资源利用率和效率的多维特征化。利用Hydra，我们评估了三代连续的边缘片上系统（SoC）（AGX Xavier、AGX Orin和AGX Thor）、来自七个家族的13个指令调优LLM、五种执行格式，并考虑了输入/输出长度敏感性。所得产物包含约10.7万条逐提示记录，并随Hydra公开发布。我们的分析表明，仅聚合延迟会掩盖关键的部署效应：后端结构会改变延迟引入的位置，量化减少了内存流量和能耗但并不能单调预测功耗，而SoC代际改变了利用率和效率的解释方式。通过将阶段级计时与系统资源利用率和效率指标联系起来，Hydra实现了边缘LLM推理的可复现、阶段感知特征化。Hydra的源代码和收集的逐提示跟踪语料库可在以下开源地址获取：https://github.com/amirtaherin/hydra

## Abstract
Edge LLM deployment is shaped by more than model size and precision: inference backend, hardware platform, memory traffic, and power management all affect latency and efficiency. We present Hydra, a common-schema, phase-aware workload characterization framework for LLM inference on edge SoCs. Hydra instruments HuggingFace Transformers and llama.cpp with a shared per-prompt timing schema and fuses those records with hardware telemetry, enabling a multi-dimensional characterization of performance, system-resource utilization, and efficiency across prefill and decode phases. Using Hydra, we evaluate three consecutive edge System-on-Chip (SoC) generations (AGX Xavier, AGX Orin, and AGX Thor), 13 instruction-tuned LLMs from seven families, five execution formats, and consider input/output-length sensitivity. The resulting artifact contains roughly 107K per-prompt records and is publicly released with Hydra. Our analysis shows that aggregate latency alone hides key deployment effects: backend structure changes where latency is introduced, quantization reduces memory traffic and energy but does not predict power monotonically, and SoC generation changes how utilization and efficiency should be interpreted. By connecting phase-level timing with system-resource utilization and efficiency metrics, Hydra enables reproducible, phase-aware characterization of edge LLM inference. Hydra's source code and the collected per-prompt trace corpus are available open-source at: https://github.com/amirtaherin/hydra

## 1. 核心问题与研究动机

- **背景**：大语言模型（LLM）已从研究工具演变为生产级基础设施，但数据中心部署与边缘部署存在根本差异。边缘SoC（如NVIDIA Jetson系列）采用CPU/GPU统一内存，受严格功耗与热预算约束，依赖平台特定的DVFS与遥测接口，这带来了数据中心LLM服务系统未面对的边缘特有瓶颈。
- **现存问题**：尽管已有大量边缘LLM推理特征化工作（单平台深挖、移动端基准、性能模型、成本—延迟—隐私权衡分析等），仍存在三个方法论缺口：
  1. 同一边缘SoC家族内的跨代比较有限，难以揭示微架构演进对推理行为的影响；
  2. 大多数研究只采用Python框架路径（HuggingFace Transformers）或C++/GGML路径（llama.cpp）之一，缺少统一的逐提示（per-prompt）、阶段感知计时模式，无法直接对比后端差异；
  3. 计时与硬件遥测很少在同一阶段边界上融合，导致无法比较不同后端、精度和平台下的解码阶段功耗、内存流量或每token能量。
- **核心论点**：仅报告聚合端到端延迟、吞吐量或运行平均功耗会掩盖prefill与decode阶段的各自贡献；量化等被广泛认为有益的技术，其功耗行为并非单调可预测；SoC代际差异也会改变利用率和效率的解读方式。因此需要一种相位感知、后端感知和平台感知的统一表征框架。

## 2. 方法论：Hydra框架

Hydra的核心思想是将“可观测性”视为一个栈：token级计时、阶段级（prefill/decode）计时、SoC级资源信号和效率级功耗/能耗/热行为，通过统一的逐提示模式对齐多源数据。

### 2.1 公共计时模式（Common Timing Schema）

- 对两种结构不同的推理后端进行插桩：
  - **HuggingFace Transformers**（Python，高层框架）；
  - **llama.cpp**（C++，基于GGML张量库）。
- 两个后端均按同一 schema 记录：tokenization、prefill阶段、逐token生成、de-tokenization、TTFT（首token时间）、ITL（token间延迟）、端到端延迟及起止时间戳。
- 为避免测量异步kernel启动而非已完成GPU工作，Hydra同步CUDA依赖区域（Python端用`torch.cuda.synchronize()`，C++端用`llama_synchronize()`）。llama.cpp还额外记录内部性能计数器用于验证。

### 2.2 阶段窗口定义与遥测融合

- 定义**prefill阶段窗口**：`[t_start, t_start + τ_tok + τ_prefill]`，覆盖tokenization与prefill阶段；
- 定义**decode阶段窗口**：`(t_start + τ_tok + τ_prefill, t_end]`，覆盖自回归生成与de-tokenization。
- 以这两个窗口为连接点，将硬件遥测（通过`tegrastats`和NVML采集的CPU、GPU、内存控制器、电源、能耗、温度信号）按同一时间基准聚合到每个时间窗口，生成统一的逐提示记录。

### 2.3 跨平台规范化模式（Canonical Cross-Platform Schema）

- 不同Jetson代际的原始遥测字段不同（CPU核数、GPU组织、热区名称、电源轨标签、软件栈支持等），Hydra将它们映射到共享字段（CPU负载、GPU活动、内存控制器行为、RAM使用、功率、温度），并保留来源信息。
- 归一化是保守的：不掩盖测量不对称性（某些GPU利用率和功率通道来自不同接口或代表不同功率域），在跨平台比较时显式解释这些差异。

### 2.4 验证

- 通过构造保证公共模式的一致：共享列在两套profiler中使用相同公式。
- 与llama.cpp内部计数器对比：prefill时间差异在0.1 ms以内，逐token生成时间差异约0.06–0.08 ms（差异来自Hydra的logit读取与贪婪argmax代价），差异有界且可解释。

## 6. 主要结论与发现

1. **性能是后端、模型架构、精度和序列长度的联合函数**：
   - 端到端延迟上，Thor比Xavier快2.8–2.9×（HF bf16），但Thor/Orin差距随模型变化（LL-1B约2.9×，GE-7B约1.4×）。
   - llama.cpp在同等16位下优于HuggingFace，小模型上优势更大（运行开销占比高）。
   - Q4_K_M显著提升解码吞吐（小模型在Xavier上可达25–60 tok/s），但7–8B模型仍按SoC代际压缩在不同范围（Thor 35–44，Orin 22–28，Xavier 13–16 tok/s）。
   - 阶段归因显示：HuggingFace的ITL远高于实际生成时间（QW-7B在Thor上生成33.0 ms但ITL达63.5 ms，差额源于de-tokenization和逐步骤开销）；llama.cpp的de-tokenization亚毫秒，ITL≈生成时间（58.6 vs 58.5 ms）。因此llama.cpp端到端更快的优势来自更低运行时开销，而非更快kernel。
   - 输入长度增加使TTFT近似线性增长（1k→5k，TTFT增加约5.0–5.7×）；输出长度增加对解码吞吐几乎无影响（仅几个百分点），主要累加稳态解码成本。

2. **资源利用率解释了性能趋势**：
   - **CPU侧行为**：HuggingFace在每token步骤中暴露大量CPU编排（Xavier全核峰值频率、Orin调度迁移、Thor集中少数核）；llama.cpp使CPU负载降至15%以下，几乎消除逐步骤CPU活动。
   - **GPU/DRAM利用率**：同一16位精度下，llama.cpp相比HuggingFace提升GPU有效利用率和DRAM有效带宽；量化降低DRAM流量但GPU占用仍高；模型规模越大，后端差异越小（Python开销被摊销）。
   - **SoC代际影响解释方式**：Thor在长扫描中保持高解码Ueff，Orin在小模型上利用率较低，导致原始利用率计数器跨代比较需先归一化。

3. **效率不遵循延迟或位宽单调性**：
   - 低位量化（Q4_K_M）提供最低每token能耗（mJ/tok），但**总功率不单调**：Q6_K往往比Q8_0和Q4_K_M更耗电、更热，说明量化格式的unpacking/dequantization工作结构影响功耗行为。
   - Thor虽比Orin瞬时功率更高，但每token能耗更低（更高吞吐抵消功率增加）。
   - 总提示能量主要由生成长度决定（1k→5k输出约5.1–5.4×能量增长；输入1k→5k仅增加11–34%）。
   - 组合效应：从HF bf16切换到llama.cpp Q4_K_M + 从Orin换到Thor可在固定能量预算下服务超过两倍的提示数。

## 7. 优点与亮点

- **统一的跨后端阶段感知模式**：首次将HuggingFace Transformers和llama.cpp置于相同的逐提示计时和阶段窗口内，实现直接、可归因的对比。
- **全栈遥测融合**：将时序与CPU、GPU、内存、功耗、热遥测在prefill/decode相位边界对齐，突破了单维聚合报告的局限。
- **覆盖广而深**：3代SoC、13模型、7家族、5格式、长度扫描构成的大型矩阵，且全部数据公开（约10.7万条记录）。
- **严谨的执行策略**：固定batch size、贪心解码、完全GPU offload、禁用early stopping，保证均匀的工作负载和公平比较。
- **方法论可扩展**：新模型/精度/提示集只需编辑输入配置；新平台只需新增tegrastats解析器，而分析管线不变。
- **注重验证与可复现**：提供内部计数器交叉验证、Artifact附录包含两阶段评估（纯数据集复现 + 真实硬件测量管线验证），并给出定性不变量（如Q6_K功耗高于Q8_0、Q4_K_M能耗最低、llama.cpp ITL<HF ITL）。
- **量化质量与系统效应分离**：先量化质量损失，避免将质量退化混淆为系统行为。

## 8. 不足与局限

- **平台范围有限**：仅覆盖NVIDIA Jetson SoC，结论依赖Jetson软件栈、CUDA路径、tegrastats遥测和DVFS策略。论文承认可扩展至AMD、Qualcomm、Apple等平台，但尚未验证。
- **量化范围有限**：仅研究权重仅GGUF格式（Q8_0/Q6_K/Q4_K_M），未覆盖激活量化、KV cache量化、FP8、纯整数管线等，这些可能改变内存流量/反量化/能耗的平衡。
- **部署场景单一**：仅batch size 1、单流交互式推断；连续批处理、并发请求、推测解码、服务式调度可能改变吞吐与资源竞争模式。
- **模型范围有限**：仅限1–8B的稠密指令调优LLM；MoE、多模态、更大稠密模型可能展示不同行为。
- **遥测采样不对称**：tegrastats以固定壁钟间隔采样，短prefill窗口样本很少，导致prefill聚合方差较大；论文承认这一点并只按测量值报告。
- **功率遥测局限**：各平台暴露的功率轨不同，且无干净仅DRAM功率轨，无法与独立内存功率传感器等价；跨平台功率比较需谨慎。
- **未报告完整资源消耗细节**：未明确给出具体测量的总GPU时数、能耗测量方法细节或板卡数量，不便于复现能耗模型的精确成本核算。
- **最后一两位数字的舍入差异**：Artifact中提及极少数表格单元在重生成时最后一位可能相差1（如86.3 vs 86.2），虽来自手稿准备时的舍入，但提示测量精度存在微小不确定性。
