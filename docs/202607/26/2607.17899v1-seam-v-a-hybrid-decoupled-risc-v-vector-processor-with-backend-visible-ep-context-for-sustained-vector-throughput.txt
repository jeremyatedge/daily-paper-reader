# SEAM-V: A Hybrid-Decoupled RISC-V Vector Processor with Backend-Visible EP Context for Sustained Vector Throughput 

Weiying Wang and Zhiwei Zhang 

Abstract —Data-parallel workloads in deep learning and scien-tific computing continue to drive demand for higher processor throughput, energy efficiency, and scalability. The RISC-V Vector Extension (RVV) supports scalable execution through a vector-length-agnostic programming model. However, many tightly coupled implementations still rely on the scalar core to supply vector instructions one at a time, making execution susceptible to vector-instruction supply gaps, scalar-side progression delays, and conservative dependence handling in short-vector, loop-tail, and control/memory-interleaved phases. This paper presents SEAM-V, a hybrid-decoupled vector execution architecture for RVV. SEAM-V forms a continuous stream of execute packets (EPs) through task-level decoupling, local instruction supply, and VLIW-style packing. After an EP is serialized into individual requests, its EP identity and request-bound prefetch context remain visible to the dynamic vector backend, enabling same-EP candidate-hazard suppression and request-bound prefetching. The hybrid-dispatch path can also provide limited cross-EP vector overlap when the required safety conditions are satis-fied. Cross-EP dependences, dependences not exempted by the EP contract, resource conflicts, and memory ordering remain dynamically managed by the backend. Cycle-accurate RTL eval-uation shows that, compared with an Ara-based tightly coupled RVV implementation (TC), SEAM-V achieves a geometric-mean speedup of 1.34 × across 17 representative kernels. The one-dimensional variable-AVL, BLAS and matrix, and fixed-size application groups achieve speedups of 1.50 ×, 1.25 ×, and 1.27 ×,respectively. At AVL=32, the geometric-mean speedup across six one-dimensional vector kernels approaches 3 ×.

Index Terms —RISC-V Vector Extension, hybrid-decoupled execution, execute packet, vector-instruction supply, backend cooperation.

Their high-throughput demands continue to drive general-purpose pro-cessors toward vector architectures. The RISC-V Vector Ex-tension (RVV) provides an open, scalable, and vector-length-agnostic programming model, offering a unified interface for software portability and performance scaling across imple-mentations with different physical vector lengths [1]. This orga-nization provides a clean interface and broad compatibility. However, vector execution remains paced by instruction-at-a-time issue from the scalar core, making it difficult to sustain a sufficiently dense and continuous stream of work in the vector backend [2]. Moreover, front-end-visible semantics, including loop structure, local parallelism, and memory-access intent, are not naturally propagated with the command stream into the backend, limiting the opportunities for scheduling, dependence handling, and memory-access coordination. These limitations arise across practical workloads with different granularities and characteristics. Short vectors, loop tails, small-batch operators, and small-matrix computations reduce the ability of vector instructions to amortize scalar-control, address-update, and issue overheads, thereby expos-ing instruction-throughput bottlenecks. Kernels with frequent control and address updates are constrained by scalar/vector interleaving, whereas regular but memory-sensitive kernels can lose execution continuity because of memory stalls and conser-vative backend scheduling. Even when an application exposes substantial data-level parallelism at a coarse granularity, its execution efficiency can still be jointly constrained by vector granularity, control intensity, and memory-access behavior. Therefore, the bottleneck of conventional tightly coupled RVV execution is not limited to short-vector scenarios. Across dif-ferent kernel classes, it commonly manifests as discontinuous execution caused by insufficient vector-instruction throughput, scalar-side progression constraints, and conservative backend execution [2], [3]. Existing approaches improve vector execution efficiency mainly through stronger instruction supply, optimized dynamic vector backends and memory paths, decoupled or streaming execution, and explicit representation of local parallelism. One class of designs employs more capable supply paths, dynamic scheduling, chaining, and memory-system optimizations to improve vector-request delivery, execution overlap, and tol-erance to long-latency events [3]–[5]. Another class reduces dependence on instruction-at-a-time control by the host scalar core and lowers fine-grained synchronization overhead through local instruction supply or by decoupling control, memory ac-cess, and computation [6]–[8]. Meanwhile, VLIW/EPIC archi-tectures explicitly organize local instruction-level parallelism using software- or compiler-generated execution packets [9], arXiv:2607.17899v1 [cs.AR] 20 Jul 2026 2

[10]. Our prior work further introduced a VLIW-driven hybrid-decoupled vector architecture that integrates task-level decou-pling, local instruction supply, scalar execution, and HINT-guided dynamic EP formation within the vector coprocessor, allowing it to progress autonomously after task submission by the Host [11]. However, front-end-generated structured information may still be lost when EPs are serialized into individual vector requests, forcing the dynamic vector backend to continue making dependence and memory-access decisions primarily from isolated requests and run-time state and thereby introducing unnecessary conservative handling. Therefore, the central problem addressed in this work is how to preserve EP ownership, loop context, and memory-access intent across the interface and make them continuously available to the back-end, while retaining the execution capabilities and correctness guarantees of a dynamic vector backend. This paper presents SEAM-V, a hybrid-decoupled vector execution architecture for RVV. SEAM-V uses an execute packet (EP) as the fundamental organizational unit connecting front-end supply and backend execution. Through task-level decoupling, local instruction fetch, scalar control, and VLIW-style organization, the front end restructures a fine-grained interleaved scalar/vector instruction stream into a continuous stream of EPs. Software uses lightweight HINT headers whose 

p-bits, loop markers, and prefetch fields expose packet bound-aries, local parallelism, loop attributes, and memory-access intent. Hardware uses these annotations to form EPs and gener-ate backend-visible EP context. SEAM-V further preserves key EP context across the front-end–backend interface, allowing the vector backend to reduce conservative dependence stalls introduced by the instruction-at-a-time request interface and to perform controlled prefetching for regular vector memory accesses. The hybrid execution path can also provide limited cross-EP vector-execution overlap when the required safety conditions hold. Without changing the computational seman-tics of standard RVV instructions, true dependences, memory ordering, and completion state remain dynamically maintained by the vector backend. SEAM-V instead improves pipeline coordination among scalar control, vector computation, and memory access. This paper develops, implements, and evalu-ates this EP-centric execution model and demonstrates its abil-ity to improve sustained execution efficiency across different vector granularities and kernel characteristics. Section VI concludes the paper. II. B ACKGROUND AND RELATED WORK 

This section first introduces the spatio-temporal execution characteristics of RVV and the vector-instruction supply con-straints of tightly coupled organizations. It then reviews prior work on scalable vector microarchitectures, dynamic back-end scheduling, decoupled and streaming execution, backend memory-path optimization, and explicit instruction grouping. Based on this discussion, we identify the execution semantic gap between the front end and backend and position SEAM-V within the resulting design space. 

A. RVV and Spatio-Temporal Vector Execution 

SIMD and vector architectures both exploit data-level par-allelism, but organize it differently. In a fixed-width SIMD ar-chitecture, the number of elements processed by an instruction is determined primarily by the ISA-visible register width and element type, and is therefore largely fixed at the architectural level. In contrast, a vector architecture decouples the architec-tural vector length from the physical datapath width. A vector instruction is expanded into a stream of element operations according to run-time state, with these operations progressing spatially across multiple lanes and temporally across multiple beats [1], [2]. In RVV, vl determines the number of active elements processed by the current instruction, while SEW and LMUL specify the element width and register grouping, respectively. The number of physical lanes and the available backend 3

resources determine how the element operations are distributed across space and time, while masking further determines which active elements update architectural state. Vector memory operations are also constrained by their access modes, address generation, and memory-system state. An RVV backend is therefore not merely a fixed-width SIMD datapath, but a stateful execution system that dynamically tracks execution progress, data dependences, resource conflicts, and memory ordering [1]. These spatio-temporal execution characteristics fundamen-tally constrain packet-based execution for RVV. Front-end packet formation can expose local program structure, but cannot statically determine the actual execution progress of vector instructions in the backend. Packet-level information relevant to backend cooperation should therefore augment, rather than replace, the run-time state of a dynamic vector backend. Vector-instruction expansion, cross-EP dependences and dependences not exempted by the EP contract, resource availability, execution progress, and memory ordering remain under dynamic backend management. 

B. Scalar-Driven Supply Constraints in Tightly Coupled RVV Processors 

Many existing RVV processors adopt a tightly coupled organization in which the host scalar core performs instruction fetch, decode, control-flow management, base-address and loop-state maintenance, and vector-instruction issue, while the vector unit receives and executes vector commands individ-ually. This organization reuses the existing scalar fetch and control paths and provides a clean scalar–vector interface. However, in systems that issue vector instructions one at a time, the scalar core remains on the critical supply path for vector-request generation. Branches, loop-control and address-state updates, and frequent vset configurations may lie on the program-order or state-dependence paths of subsequent vector requests. Delays in advancing these operations can therefore introduce supply gaps between consecutive requests [2], [11]. When vectors are short or scalar and vector operations are frequently interleaved, each vector instruction amortizes less control, state-update, and issue overhead. Even if the vector backend provides substantial data-parallel execution capacity, its vector-instruction supply remains constrained by the progression rate of the scalar path. Intermittent request arrivals may prevent the lanes and memory resources from operating continuously. This limitation is therefore not merely a scalar-front-end fetch or decode bandwidth problem, but an end-to-end supply constraint jointly imposed by scalar-state progression, vector-request generation, and instruction-at-a-time issue [2], [5]. 

C. Related Execution Models and the Semantic Gap 

Prior work has improved vector-processor efficiency through scalable microarchitectural organizations and dynamic backend scheduling. Ara and Ara2 employ scalable lane-based organizations to support long-vector execution and show that scalar-core issue rate can become a performance constraint for short vectors [2], [12]. Spatz improves area and energy efficiency through compact vector units integrated into large-scale shared-L1 clusters [13]. Classical out-of-order vector architectures introduce register renaming and out-of-order issue into vector processors [4]. OVPM further explores out-of-order execution for short-vector workloads [14], while CODE improves vector-register-file scalability and hides communication and memory latency through a clustered vector register file, rename structures, and execution decoupling [15]. For RVV, Vitruvius+ com-bines in-order and out-of-order execution, register renaming, and arithmetic–memory decoupling [16], whereas Saturn uses dynamic scheduling and chaining to improve short-vector execution efficiency [5]. Titan-I further combines a scalable lane-based out-of-order architecture with issue-as-commit, fine-grained chaining, and memory interleaving to improve scalar/vector concurrency, dependent-instruction progress, and memory-level parallelism [17]. Another class of work improves execution continuity through decoupled supply, streaming semantics, or backend memory-path optimization. The vector-thread model of Scale and the decoupled vector-fetch architecture of Hwacha allow data-parallel execution to maintain a local instruction supply outside the control core [6], [18]. Decoupled Access/Execute separates access and execution streams using queues, allowing address generation and memory access to progress ahead of computation [7]. Stream Semantic Registers map regular memory accesses onto implicit register accesses, thereby re-ducing explicit load/store and address-update instructions [8]. Snitch’s FREP mechanism repeatedly supplies floating-point instructions from a micro-loop buffer, reducing the need for continuous instruction delivery from the integer control pipeline [19]. On the backend memory side, TROOP shows that widening the L1 interface alone is insufficient for low-operational-intensity workloads to reach the bandwidth roofline. It com-bines decoupled load/store interfaces, improved vector chain-ing, shadow buffers for hiding VRF conflicts, and TCDM address scrambling to better coordinate memory throughput with compute-pipeline progress [3]. Decoupled Vector Runa-head represents a related approach that speculatively vectorizes indirect memory-access chains to generate future requests and hide irregular memory latency [20]. Complementary to dynamic scheduling and decoupled ex-ecution, VLIW/EPIC and several DSP architectures explicitly expose local instruction-level parallelism through software-or compiler-generated annotations that organize parallel op-erations into instruction bundles or execution packets [9], [10]. SLAP further relaxes the lockstep constraint among conventional VLIW functional units and supports SIMD vector lengths that vary at run time [21]. For RVV, however, each vector instruction must still be dynamically expanded over multiple beats according to vl , SEW, LMUL, and the number of physical lanes. Its actual progress, resource occupancy, data dependences, and memory ordering cannot be fully determined by front-end grouping. Explicit instruction grouping can there-fore expose local program structure, but cannot replace the run-time execution management of a dynamic RVV backend. Overall, prior work improves vector execution through 4

scalable vector organizations, dynamic backend scheduling, decoupled or streaming execution, backend memory opti-mization, and explicit parallelism representation. A design that combines front-end execute-packet organization with an instruction-at-a-time dynamic RVV backend must additionally preserve information across changes in execution granularity. Once a front-end-generated packet is decomposed or serialized into individual vector requests, EP ownership and memory-access intent may be lost unless they are explicitly carried across the interface. Similarly, loop-active state may no longer remain continuously available to the backend memory path. The vector backend must then make dependence and memory-access decisions primarily from individual requests and run-time state, potentially introducing unnecessary conservative handling. We refer to this inability to preserve and reuse front-end structured information across execution-granularity conversion as the front-end–backend execution semantic gap. 

D. Positioning of SEAM-V 

SEAM-V lies at the intersection of decoupled vector execu-tion, execute-packet organization, and dynamic RVV backend optimization. Its defining feature is not a simple combina-tion of these mechanisms, but the continuity of EP context across task-level execution, local instruction organization, and dynamic backend execution. Hot kernels progress through a local hybrid execution path, where interleaved scalar/vector instructions are organized into EPs. After an EP is hybrid-dispatched and its vector slice is serialized into individual requests, the associated context remains visible to the backend. SEAM-V does not use EPs to replace run-time backend management. Instead, backend-visible EP context augments the dynamic RVV backend with packet-level information that would otherwise be lost during request serialization. Vector-instruction expansion, cross-EP dependences and dependences not exempted by the EP contract, resource conflicts, execution progress, and memory ordering remain dynamically managed by the backend. This paper studies the complete execution path compris-ing task-level hybrid decoupling, HINT-guided EP formation, hybrid dispatch, backend-visible EP-context propagation, and EP-driven backend cooperation. Compared with our prior work [11], this work further preserves EP context across the instruction-at-a-time request interface, enables the dynamic backend to consume that context, and completes the end-to-end RTL integration of same-EP candidate-hazard suppression and request-bound prefetching. The evaluation further includes ablation and sensitivity analyses, together with synthesis and physical-design evaluation, to quantify the performance, energy-efficiency, and hardware costs of the key mechanisms. III. SEAM-V H ARDWARE ARCHITECTURE 

This section presents the SEAM-V hardware architecture. We describe how the hybrid-decoupled execution path forms and dispatches execute packets (EPs), how EP context is generated and propagated to the dynamic RVV backend, and how the backend uses this context to reduce conservative dependence stalls and perform request-bound prefetching. 

A. Architecture Overview 

Fig. 1 shows the overall microarchitecture of SEAM-V. SEAM-V introduces a task-level hybrid-decoupled execution path between the Host and the vector backend. This path decouples hot vector kernels from instruction-at-a-time issue by the Host and converts them into a sustained stream of EPs generated by local hardware. It comprises task management, local instruction supply and scalar execution, HINT-guided EP formation, hybrid dispatch, and backend-visible EP-context propagation. After the Host submits a kernel entry address and its execution context, the Task Schedule Unit (TSU), Instruction Prefetch Unit (IPU), VLIW Pack Unit (VLIWPU), Hybrid Execution Unit (HEU), and local scalar backend jointly per-form task scheduling, instruction supply, loop progression, EP formation, and hybrid dispatch. The VLIWPU organizes the local instruction stream into EPs, while the HEU partitions each EP into a scalar slice and a vector slice and delivers them to the scalar backend and vector backend, respectively. Each vector request carries an EP identity and request-bound prefetch context into the vector backend, whereas 

loop-active is supplied to the memory path as indepen-dent run-time state. The EP identity identifies the EP to which a request belongs, preserving same-EP membership after the EP is serialized into individual requests. Together, the EP identity and request-bound prefetch context constitute the EP context used throughout this work. An EP is the basic unit of local instruction organization and dispatch, whereas EP context is the packet-level hardware metadata that connects hybrid dispatch with vector-backend cooperation. Cross-EP dependences, requests without valid EP context, and dependences not exempted by the software EP contract remain dynamically managed by the vector backend. Resource conflicts, memory ordering, and instruction completion also re-main under backend control. The IPU, scalar LSU, and VLSU access system memory through a shared AXI interconnect, while task-completion and exception status are returned to the Host through a unified aggregation path. 

B. Hybrid-Decoupled Execution Path 

SEAM-V employs task-level decoupling to raise the software–hardware interaction granularity from individual vec-tor instructions to complete kernels. After the Host submits a task, the TSU manages pending tasks in submission order and activates one task at a time. Instruction fetch, loop control, scalar execution, EP formation, and vector dispatch are then performed entirely within the local execution domain. This organization removes the Host from the continuous vector-instruction supply path while retaining the execution context required to coordinate scalar control and vector execution within a kernel [11]. The IPU fetches 128-bit instruction packets from the task entry address and uses ping-pong buffering to overlap con-sumption of the current packet with refill of subsequent packets. C. HINT-Guided Execute-Packet Formation 

The continuous local instruction stream is organized into EPs through HINT-guided packetization [11]. A HINT header specifies the logical-packet width, whether an EP may span logical packets, loop markers, and prefetch intent. Each p-bit in the pbits field indicates whether two adjacent instruction slots may remain within the same EP. The detailed encoding and software annotation rules are presented in Section IV. By default, the IPU supplies 128-bit fetch packets. When 

packet256 is asserted, two consecutive fetch packets form a 256-bit logical packet, enlarging the local observation window of the VLIWPU. The instruction stream is scanned in 16-bit slots. A compressed instruction occupies one slot, whereas a 32-bit instruction spans two consecutive slots [22]. Increasing the logical-packet width enlarges only the observation and packing window; an individual EP remains subject to a fixed maximum issue width of eight slots. The VLIWPU scans sequentially from the current valid position in a logical packet. It terminates the current EP when the p-bit chain breaks, an explicit dependence boundary is encountered, a branch or system boundary is reached, or the maximum issue width is reached. At the end of a logical packet, an EP boundary is formed if cross is disabled or the conditions for cross-packet formation are not satisfied. Otherwise, the tail fragment is buffered and combined with instructions at the beginning of the next logical packet. This mechanism prevents a physical fetch boundary from unnec-essarily truncating an EP. Downstream backpressure stalls the delivery of an already formed EP but does not alter its membership. D. Hybrid Dispatch and Backend-Visible EP-Context Propa-gation 

As shown at the bottom of Fig. 2, once an EP has been formed, the HEU reconstructs its 16- and 32-bit instructions according to their slot lengths and partitions them into a scalar slice and a vector slice based on instruction class. The scalar slice is delivered to the local scalar backend for task-level control flow, address progression, and scalar-state updates. The vector slice enters the VDU shown in Fig. 1, where it is serialized into individual requests accepted by the vector backend. Before a request enters the vector backend, the VDU captures its required scalar operands. Once captured, these operands are no longer affected by subsequent updates to the scalar register file. The VDU also binds the EP identity and request-bound prefetch context to each request. Thus, even after an EP is decomposed into individual requests at the interface, its EP membership and prefetch intent remain visible to the vector backend. SEAM-V defines vector-slice acknowledgment as an operand-safe handoff rather than completion of vector exe-cution. Once the scalar operands required by all requests in a vector slice have been captured and any required scalar-visible vset result has been returned, the VDU acknowledges the vector-side handoff. The HEU additionally waits for the scalar slice to complete before acknowledging the current EP and allowing the front end to advance. At that point, the corresponding vector instructions may still be executing in the sequencer, lanes, or memory subsystem. This separation decouples front-end progress from long-latency vector com-pletion and enables a sustained supply of EPs. To decouple EP generation from the handoff of its two slices, the HEU maintains one current EP and one buffered EP and assigns EP identities to the corresponding vector slices. A buffered scalar slice always waits for promotion before executing in program order. A buffered vector slice may be handed off early only when the required control-flow, memory-ordering, operand-dependence, and backend-resource safety conditions are satisfied. This mechanism allows vector-side work from a later EP to enter the VDU earlier under controlled conditions, without changing the ordered semantics of scalar slices or permitting unrestricted cross-EP out-of-order execution. A small command window within the VDU further decou-ples request resolution and operand snapshotting from actual request acceptance by the vector backend. During transient backend backpressure, resolved requests can remain buffered in the window and resume delivery once the backend becomes available. Each window entry retains the EP context and side-effect metadata associated with its request, preserving request-level metadata alignment throughout buffering. 

E. EP-Driven Backend Cooperation 

Once EP context enters the vector backend with each re-quest, the sequencer uses the EP identity to recognize same-EP requests and perform same-EP candidate-hazard suppression, while the VLSU and address-generation unit use the request-bound prefetch context to perform request-bound prefetching. The former reduces conservative dependence stalls reintro-duced when an EP is serialized into individual requests, whereas the latter converts software-exposed regular memory-access intent into prefetch behavior controlled by run-time backend state. The vector sequencer tracks vector-register dependences us-ing in-flight read and write state. Because the VDU serializes an EP into multiple independent requests, a backend that loses their EP membership may conservatively construct candidate dependences between same-EP requests under conventional instruction-at-a-time checking. SEAM-V therefore retains the EP identity of each in-flight request. When a new request and an in-flight request carry valid and matching EP identities, the sequencer excludes the corresponding same-EP RAW, WAR, 7

and WAW candidate entries when constructing the hazard vectors, in accordance with the EP contract. This prevents these candidates from introducing unnecessary stalls during subsequent operand requests and execution progress. This mechanism neither disables conventional dynamic dependence tracking nor makes requests unconditionally is-suable. The safety of suppressing same-EP candidates is guaranteed by the software EP contract. Cross-EP requests, re-quests without valid EP context, and dependences not covered by the contract remain subject to conventional RAW, WAR, and WAW handling. Requests must also satisfy backend queue availability, execution-resource constraints, and other run-time safety conditions before they can progress. In the vector memory path, the prefetch context remains aligned with its associated EP during EP formation and cross-packet combination. After request serialization, the VDU binds this context to the corresponding unit-stride vector-load request, preventing it from becoming misaligned with the actual request during queuing, command-window buffering, or backend stalls. For an eligible regular load stream, the 1X mode prefetches an equally sized data block immediately after the logical vector-access span of the current request. The 2X, 4X, and 8X modes advance the prefetch address by two, four, and eight logical vector spans, respectively. The address-generation unit produces a prefetch only when the request-level hint is valid and enabled, the access mode is eligible, and the remaining AVL is sufficient to cover the target range. Prefetch issue is further constrained by queue capacity, buffer credits, and recovery state. When loop-active is deasserted, the hardware stops extending the prefetch stream and drains the associated state. If the hint is invalid, the access mode is ineligible, or the required resources are unavailable, the memory path continues with normal demand-driven exe-cution. The prefetch path further limits its lookahead through ca-pacity constraints and stream-break recovery. When the actual demand stream diverges from the recorded prefetch sequence, the hardware stops extending the prefetch stream, waits for in-flight requests to drain safely, and then clears the address-matching state and prefetch buffer. This recovery prevents stale prefetched data from continuing to occupy resources or obstructing normal demand requests. Software therefore supplies only exploitable memory-access intent, while the vector backend dynamically determines whether a prefetch is generated, when it is issued, and whether it is ultimately consumed by a demand access. B. HINT Encoding and Semantic Contract 

SEAM-V uses the RISC-V HINT form lui x0, imm20 

to encode the packet-level information required for EP for-mation and backend cooperation. The instruction does not modify architecturally visible RISC-V state; in SEAM-V, its immediate field is interpreted as packet-level metadata [11], [22]. Table I summarizes the HINT-header encoding. The HINT header defines the software-visible annotation associated with a logical packet. The packet256 field en-larges the local scanning and packing window of the VLIWPU, while cross allows an unfinished EP at the end of one logical packet to continue into the next when the required conditions are satisfied. These fields affect only the VLIWPU observation window and the permission for cross-packet formation; they do not change the maximum issue width of an individual EP. 8

The pbits field is a bitmap that describes instruction connectivity within a logical packet. When the p-bit between two adjacent slots is set, the following instruction may be included in the same EP; when it is cleared, an EP boundary is formed at the corresponding position. For a 32-bit instruction, the VLIWPU reconstructs the complete instruction from two consecutive 16-bit slots, and an EP boundary cannot split the instruction [22]. Branch and system instructions are forced by hardware to terminate the current EP. Software must also clear the corresponding p-bit for data dependences or memory-ordering relationships that require dynamic backend enforce-ment, thereby placing the affected instructions in different EPs. Consequently, software guarantees that vector instructions within the same EP contain no RAW, WAR, WAW, or memory-ordering conflicts that require dynamic backend maintenance. The loop_start and loop_end fields identify a loop region that may be buffered and replayed by the local front end. The actual loop-active state is not determined solely by these static markers; instead, it is jointly maintained using the loop markers and the backward branch resolved by the local scalar path. Prefetch semantics are jointly defined by pf_disable and 

pf_mode . The former determines whether the current logical packet carries prefetch intent, while the latter selects a 1X, 2X, 4X, or 8X distance when prefetching is enabled. Their inde-pendent encodings prevent 00 from ambiguously representing both disabled prefetching and the minimum prefetch distance. The hint primarily targets eligible unit-stride vector-load streams within loops. It remains aligned with the correspond-ing EP during EP formation and cross-packet combination and is bound to the associated vector memory request after serialization. In 1X mode, the backend prefetches an equally sized data block immediately after the logical vector-access span of the current request. The 2X, 4X, and 8X modes advance the prefetch address by two, four, and eight logical vector spans, respectively. For gather/scatter operations, irreg-ular accesses, short execution phases, or access patterns that cannot be effectively represented by a fixed distance, software should disable the hint and allow the vector backend to follow normal demand-driven execution. These fields expose execution structure and define the associated software–hardware contract without changing the computational semantics of RVV instructions. Cross-EP de-pendences, dependences not exempted by the software con-tract, run-time resource conflicts, memory ordering, and state cleanup at loop exit remain dynamically managed by the vector backend.

Backend-visible EP-context propagation supports same-EP candidate-hazard suppression and request-bound prefetching, while buffered vector early issue pro-vides limited cross-EP overlap under safe conditions. After vector-instruction supply is improved, backend backpressure, command-window capacity, residual dependence stalls, and scalar-operand waits remain important sources of pressure for several workloads. VI. C ONCLUSION 

This work presented SEAM-V, a hybrid-decoupled vector execution architecture that addresses two limitations of tightly coupled RVV processors: discontinuous vector-instruction sup-ply caused by scalar-driven instruction-at-a-time issue, and the loss of EP context when execute packets are serialized into individual requests. SEAM-V forms a sustained stream of execute packets (EPs) through task-level decoupling, local instruction supply, and VLIW-style packing. It propagates EP identity and request-bound prefetch context to the dynamic vector backend, enabling same-EP candidate-hazard suppres-sion and request-bound prefetching. Buffered vector early issue further provides limited cross-EP overlap of vector-side work when the required safety conditions are satisfied. Cross-EP dependences, dependences not exempted by the EP contract, resource conflicts, and memory ordering remain dynamically managed by the backend. Cycle-accurate RTL evaluation shows that SEAM-V achieves a geometric-mean speedup of 1.34 × over TC across 17 representative kernels. At AVL=32, the geometric-mean speedup across six one-dimensional vector kernels approaches 3×. The ablation study demonstrates that the basic hybrid-decoupled path, request-bound prefetching, and same-EP candidate-hazard suppression each provide incremental perfor-mance benefits. Across seven representative kernels, the com-plete configuration reduces geometric-mean execution cycles by approximately 32.6% relative to TC. Microarchitectural analysis further reveals kernel-dependent EP organization, backend-coordination activity, and residual execution pressure. Overall, the results demonstrate that maintaining backend visibility of EP ownership and request-bound prefetch infor-mation across request serialization improves vector-instruction supply continuity and end-to-end execution efficiency for the evaluated workloads.
