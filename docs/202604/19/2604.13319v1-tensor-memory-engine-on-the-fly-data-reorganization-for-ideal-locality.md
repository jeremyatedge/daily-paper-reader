## 摘要
从云端到边缘的数据密集型处理转型，为下一代智能计算系统带来了新的挑战和期望。随着存储墙问题的日益严重，现代系统只有通过展现出在内存中具有理想布局、在缓存中具有理想时空局部性的数据访问模式，才能满足这些性能预期。然而，只有少数数据密集型应用具备理想局部性的特征。相反，大多数应用要么 (i) 在原生实现时局部性较差，必须经历昂贵的重新设计和调优；要么 (ii) 为了提供适当的局部性而导致内存占用膨胀。为了应对上述挑战，我们提出了一种软硬件协同设计的方法，该方法可以在商用 SoC/FPGA 平台上实现。我们的方法在 CPU 的数据路径中无缝插入了一个张量内存引擎（Tensor Memory Engine），通过 (i) 代表 CPU 访问内存以及 (ii) 构建内存布局的重组视图，为运行中的应用提供具有理想缓存局部性的数据。与存内计算和近存计算方法不同，该引擎的独特之处在于清晰地解耦了计算与内存访问；计算仍由 CPU 执行，而数据重组则委派给张量内存引擎。

## Abstract
The shift to data-intensive processing from the cloud to the edge has introduced new challenges and expectations for the next generation of intelligent computing systems. As the memory wall continues to grow, modern systems can only meet these performance expectations by displaying data access patterns that exhibit ideal layouts in memory and ideal spatiotemporal locality in caches. However, only a few data-intensive applications are characterized by ideal locality. Instead, most applications exhibit either (i) poor locality when naively implemented and must undergo costly redesigns and tuning or (ii) inflated memory footprint to offer proper locality.   To address the aforementioned challenges, we propose a hardware/software co-designed approach that can be implemented on commercially available SoC/FPGA platforms. Our approach seamlessly inserts in the CPUs' data path a Tensor Memory Engine that provides data with an ideal cache locality to running applications by (i) accessing the memory on behalf of the CPUs and (ii) composing a re-organized view of the memory layout. Unlike in- and near-memory computing approaches, it sets itself apart by clearly decoupling computing and memory accesses; computation is still performed on CPUs while the data re-organization is delegated to the Tensor Memory Engine.

### 1. 核心问题与整体含义（研究动机和背景）
*   **核心挑战：** 随着计算与内存性能差距（存储墙）不断扩大，数据密集型应用（如 AI、计算机视觉）的性能高度依赖于缓存的**时空局部性**。
*   **现状痛点：** 
    1.  **局部性差：** 许多高维数据（张量）在内存中的物理布局与算法的访问模式不匹配，导致缓存命中率低。
    2.  **优化成本高：** 开发者通常需要手动重写算法（如分块、转置）或在内存中复制一份重组后的数据，这既耗时又增加了内存占用（Working Set Size, WSS）。
*   **研究动机：** 能否在不修改算法逻辑、不增加内存副本的前提下，让 CPU 看到的内存布局永远是“理想”的？

### 2. 方法论：核心思想与关键技术
*   **核心思想：** **计算与数据布局重组的解耦**。引入一个位于 CPU 数据路径上的硬件引擎（TME），它代表 CPU 访问内存，并将离散的物理数据实时组装成连续的缓存行（Cacheline）返回给 CPU。
*   **关键技术细节：**
    *   **内存语义转换：** TME 将“重组后的数据空间”映射到“原始物理空间”。
    *   **三阶段流程：**
        1.  **地址分解（Address Decomposition）：** 根据预设的 N 维步长（Stride）模式，将 CPU 的一个缓存行请求拆分为多个物理内存片段请求。
        2.  **内存访问（Memory Access）：** 并行从 DRAM 中获取这些片段。
        3.  **结果聚合（Result Aggregation）：** 将获取的片段拼装成完整的缓存行，通过一致性接口（如 ACE 协议）返回给 CPU 缓存。
    *   **访问模式规范：** 使用一组元组 $( \omega, \sigma, w )$ 来定义每一维的初始偏移、步长和长度，支持转置、切片、重塑（Reshape）等复杂操作。

### 3. 实验设计
*   **硬件平台：** AMD-Xilinx UltraScale+ Kria KR260 开发板（含四核 ARM Cortex-A53 CPU 和 FPGA 逻辑）。
*   **软件环境：** Ubuntu 22.04，自定义 Linux 内核驱动和用户态库。
*   **Benchmark（基准测试）：** 选取了 7 种典型的张量操作：
    *   **Im2col：** 卷积中的图像转矩阵操作。
    *   **Conv2D：** 朴素 2D 卷积。
    *   **Permutation：** 维度置换（如 HWC 转 CHW）。
    *   **Unfolding：** 张量展开。
    *   **Batch2Space：** 批次到空间的转换。
    *   **MatMul：** 矩阵乘法（含转置优化）。
    *   **Slicing：** 多维张量切片。
*   **对比对象：** 纯 CPU 实现的基准版本（Baseline）。

### 4. 资源与算力
*   **硬件规格：** CPU 频率 1.3 GHz，FPGA 逻辑频率 300 MHz，1MB L2 缓存，4GB DDR4 内存。
*   **算力说明：** 论文未涉及大规模 GPU 训练，其核心在于 **SoC 内部的访存架构优化**。TME 作为一个硬件模块集成在 FPGA 逻辑中，通过 AXI/ACE 接口与 CPU 互联。

### 5. 实验数量与充分性
*   **实验规模：** 针对 7 种不同的算子进行了性能（加速比）和内存占用（WSS）的定量分析。
*   **充分性评价：** 实验覆盖了主流的张量变换模式，且在**真实硬件**（而非纯模拟器）上运行，结果具有较高的可信度。论文还专门讨论了不同数据类型（uint8 到 uint64）对带宽的影响，体现了实验的深度。

### 6. 主要结论与发现
*   **性能提升：** TME 在大多数任务上实现了加速，其中 **Slicing（切片）操作获得了最高的 1.77x 加速**，主要得益于将随机离散访问转换为了线性流式访问。
*   **内存节省：** 显著降低了瞬时内存占用。例如在 Im2col 中，传统方法需要生成巨大的中间矩阵，而 TME 实现了“零拷贝”实时重组。
*   **带宽瓶颈：** 发现当处理极小元素（如 1 字节的 uint8）时，TME 会触发大量的细粒度 DRAM 访问，导致有效带宽下降。这是因为商用内存控制器是为 64 字节缓存行优化的，而非小片段。

### 7. 优点
*   **透明性：** 对上层应用透明，无需修改核心算法逻辑。
*   **零数据冗余：** 避免了为了优化局部性而进行的物理数据复制，对边缘设备（内存受限）极具价值。
*   **软硬件协同：** 充分利用了现代 SoC 中 FPGA 逻辑的灵活性，将其作为数据路径的一部分而非简单的加速器。

### 8. 不足与局限
*   **硬件依赖：** 需要特定的 SoC/FPGA 架构支持一致性接口（如 ACE），在纯通用 CPU 上无法实现。
*   **小元素效率问题：** 如结论所述，在处理细粒度数据类型时，受限于现有 DRAM 控制器的突发传输（Burst）机制，性能可能受损。
*   **应用限制：** 目前主要针对稠密张量（Dense Tensor），对于稀疏数据的支持尚未讨论。
